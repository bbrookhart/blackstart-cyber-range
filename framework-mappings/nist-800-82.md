# NIST SP 800-82 Rev. 3 — Guide to Operational Technology (OT) Security

**Informational orientation. Not a conformance claim.**

SP 800-82r3 is BLACKSTART's principal OT security reference. This document
relates the project's design decisions to the publication's guidance at the level
of *principle*, and states plainly where BLACKSTART does not follow it.

Reference: NIST SP 800-82 Rev. 3 (final, 2023). Where a newer revision exists in
draft, draft guidance is not used here; this document tracks the current final
publication.

---

## Why OT is treated differently

The publication's central argument is that OT security cannot be enterprise IT
security transplanted, because the priorities differ. BLACKSTART is built around
that argument rather than merely citing it.

| OT consideration | How BLACKSTART reflects it |
| --- | --- |
| **Safety first** | Consequence classes escalate to C4/C5 only on *physical* evidence — a violated safety invariant or containment loss. A confidentiality or integrity event that does not reach the process does not escalate. |
| **Availability over confidentiality** | Service availability is a headline metric. Confidentiality is not modelled at all, because in this process it is not the property under threat. |
| **Deterministic operation** | Fixed 0.5 s integration step; sampled 1.0 s control scan; no wall-clock dependence anywhere in the kernel. |
| **Performance and timing** | Control action is quantised and slightly stale by construction, so reaction latency is part of every result rather than assumed away. |
| **Equipment constraints** | Anti-cycling limits, actuator slew limits, dry-run protection, and a pump curve that falls with head — all modelled because they bound what a command can physically achieve. |
| **Degraded-mode operation** | SCN-005 measures continued control under lost supervisory visibility. Reserve protection trades delivered service for reserve volume. |
| **Recovery** | Measured from the end of a disturbance to sustained restoration of the critical function, and explicitly reported as undefined when a disturbance persists. |

## Architecture and segmentation

The publication's architectural guidance — layered zones, a demilitarised zone
between enterprise and OT, brokered rather than direct flows — is implemented
literally and then **tested**, which is the part that matters.

- Four zones, four isolated networks, one bridging service per conduit.
- No service holds both an enterprise network and an OT-side network except the
  DMZ broker; reaching the controller from the enterprise zone requires three
  hops through three services.
- Telemetry is pulled outward. No control command originates outside the OT
  supervisory zone.
- The DMZ broker narrows what crosses: six process fields cross outward; setpoint
  and command detail do not.
- Exactly one host-published port, bound to loopback.

`tests/architecture/` parses `configs/architecture.yaml` and `docker-compose.yml`
and fails if they disagree. A segmentation claim nobody checks decays into a
segmentation claim that is false.

**Honest limitation:** Docker bridge networks demonstrate *topology*, not
enforcement strength. They are not equivalent to physically separate networks
with an inspecting firewall, and BLACKSTART does not claim otherwise.

## Risk management

BLACKSTART performs **consequence analysis**, not risk assessment.

It enumerates what can reach the physical process and how severe the result would
be. It estimates **no likelihoods**, because it has no basis for estimating them
— a simulation of a fictional process cannot tell you how probable anything is in
a real one.

This is a deliberate restriction. A risk number derived from an invented
likelihood would be the most misleading artefact this project could produce.

## Where BLACKSTART does not follow the guidance

Stated directly, because a mapping that lists only agreements is advertising.

| Area | Status |
| --- | --- |
| Identification and authentication | **Absent.** No authentication anywhere. Acceptable only because nothing is exposed beyond loopback; it would be indefensible in a real deployment. |
| Access control and least privilege for users | **Absent.** No user model exists. |
| Cryptographic protection | **Absent.** All internal traffic is plain HTTP on internal Docker networks. |
| Continuous monitoring and detection | **Absent.** No detection analytic and no network telemetry. Detection metrics are `NOT_IMPLEMENTED`. |
| Configuration and change management | Partial: configuration is versioned, hashed and validated, but there is no change-control process. |
| Physical security | Out of scope entirely. |
| Personnel and training | Out of scope entirely. |
| Incident response process | **Absent.** BLACKSTART produces the evidence a responder would want; it does not model responding. |
| Supply chain | Partial: dependency auditing, SBOM generation, pinned base images, lockfile-only installs. |

A reader should conclude that BLACKSTART implements a small number of the
publication's architectural and engineering ideas thoroughly, and most of its
programmatic guidance not at all.
